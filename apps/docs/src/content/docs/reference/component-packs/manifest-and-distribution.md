Once a pack's components compile and pass tests, they need a path to
the browser. This page covers the wiring.

## View opt-in — the `packs:` manifest key

A view opts into a pack by listing it in its manifest. Example
(`.ship/views/git/manifest.jsonc`):

```jsonc
{
  "name": "git",
  "type": "html",
  "description": "Git status, log, and diff viewer",
  "claims": [],
  "packs": ["git"]
}
```

The daemon reads the manifest at render time and injects
`<script type="module" src="/api/assets/<bundle>.js">` tags
into the response — into `<head>` for a full-page load, at the top of
the body for a Datastar fragment navigation. The shell only eagerly
loads the two core bundles (`datastar.js`, `ship-elements.js`); every
pack bundle arrives per-view. Source of truth:
`apps/shipd/src/views/packs.rs`.

Unknown pack names are silently dropped — the lint rule
`stale-pack-declaration` surfaces typos at author time.

## Pack → bundle mapping

The daemon maps pack names to bundle filenames in `pack_bundles` in
`apps/shipd/src/views/packs.rs`. Today:

| Pack | Bundles emitted |
|---|---|
| `editor` | `ship-code-editor.js`, `ship-markdown-editor.js` |
| `terminal` | `ship-terminal.js` |
| `git` | `ship-git.js` |

Adding a first-party pack means adding a match arm there and a bundle
script in `packages/ship-set/package.json`.

## Bundle scripts

`packages/ship-set/package.json` ships one `bundle:*` script per
bundle. The git pack's script is the template for a new pack:

```json
"bundle:git": "esbuild src/packs/git/index.ts --bundle --format=esm --target=es2020 --outfile=../../apps/shipd/assets/ship-git.js --log-level=warning"
```

The output lands in `apps/shipd/assets/`, which the daemon serves at
`/api/assets/<filename>`.

## Custom-elements manifest (CEM)

`packages/ship-set/custom-elements.json` is generated by
`custom-elements-manifest analyze` via `pnpm -F @ship/set manifest`.
It is the machine-readable catalog of every `<ship-*>` tag: attrs,
props, slots, events, CSS custom properties, types, defaults.

Sources of truth:

- **Repo:** `packages/ship-set/custom-elements.json` (~190KB).
- **Daemon URL:** `GET /api/assets/custom-elements.json`.
- **Compact catalog:** `GET /api/assets/ship-elements.md`
  (machine-generated, ~4KB, one line per element).

The manifest analyzer walks `packages/ship-set/src/**/*.ts`, so pack
components are picked up automatically if their JSDoc header follows
the documented conventions (see
[Authoring](./authoring.md#minimal-lit-component)). IDE tooling
(lit-plugin, lsp-cem, VS Code) consumes the CEM for attribute
autocomplete and type checking. Agents consume the compact catalog for
in-context retrieval.

## Pro-pack distribution

Pro-packs — packs sold or licensed outside the Ship monorepo — ship
as standalone npm packages:

- `package.json` with `peerDependencies: { "@ship/set": "^x.y" }`.
  Do not bundle `@ship/set` — the host already has it.
- A bundled ESM artifact (e.g. `dist/<pack>.js`) the consuming daemon
  serves under `/api/assets/`.
- A generated `custom-elements.json` shipped in the package so agents
  in the consumer's project discover the new `<ship-*>` tags.
- A short README documenting the `packs: ["<name>"]` manifest value
  and any runtime dependencies.

The `agents discover the new tags` path assumes the consumer wires the
pack's CEM into their compact-catalog retrieval. CEM retrieval for
external packs is not yet wired end-to-end (see the [roadmap](./roadmap.md)).

## Licensing and pricing

Per-pack pricing, entitlement checks, and commercial licensing are
**product concerns, not technical ones**. Keep them off the component
surface. Gate at install-time or at daemon registration, not inside
the component's `connectedCallback`. This document has nothing
prescriptive to say about price points or license terms.
