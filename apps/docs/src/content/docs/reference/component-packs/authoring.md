Once the decision tables in [When to author](./when-to-author.md) say
yes, this page covers the mechanics.

## Directory layout

**First-party pack** (lives in the monorepo):

```
packages/ship-set/src/packs/<pack-name>/
  index.ts               <- pack entry point; re-exports + side-effect imports
  ship-<element>.ts      <- one component per file
  ship-<element>.test.ts <- colocated tests
```

The reference in-tree pack is `packages/ship-set/src/packs/git/`
(`index.ts`, `ship-file-row.ts`, `ship-branch-row.ts`). Read it before
writing anything.

**Pro-pack** (external npm package):

```
<your-package>/
  package.json           <- peerDependencies: { "@ship/set": "^x.y" }
  src/
    index.ts
    ship-<element>.ts
    ship-<element>.test.ts
  custom-elements.json   <- generated by custom-elements-manifest
  dist/
    <pack-name>.js       <- bundled ESM, published alongside CEM
```

Pro-packs follow the same authoring rules as first-party packs. The
only difference is the distribution channel (see
[Manifest & distribution](./manifest-and-distribution.md)).

## The distribution test

Verbatim from `.ship/skills/ship-components/SKILL.md` — before you
write a new `<ship-*>` element, **at least one** of these must be true:

1. **Semantic primitive** — it has a known name in UI vocabulary. A
   web developer recognizes the name without seeing the element
   (button, card, combobox, list-tile, popover, tabs, badge). Mirrors
   what Radix, Material, or iOS would call it.
2. **Platform concept** — it represents a domain object whose
   rendering is structurally tied to the concept (Ship's
   `ship-pipeline-step` qualifies because "pipeline step" has a
   specific shape). For a pack, substitute *your* domain: a
   `ship-gantt-task` in a project-management pack is legitimate if the
   rendering encodes the concept.
3. **Has its own brain** — non-trivial internal logic that justifies
   isolation: Monaco, xterm, tiptap, a custom layout engine.

If an element fails all three, it is a **composition**, not a library
element — it belongs in a Jinja partial under the consuming view's
`_components/`, not in the pack. Never ship a thin wrapper whose only
value is filling slots with view-specific content.

See [ship-components charter](https://github.com/) (loaded via the
`ship-components` impl skill) for the full rationale, including the
tier classification (`core / islands / domain / viz`).

## Minimal Lit component

Copy from a real in-tree component — don't start from scratch. The
simplest reference is `packages/ship-set/src/packs/git/ship-file-row.ts`.
The template shape:

```ts
/**
 * <ship-my-thing> — one-line description.
 *
 * Props:
 *   value    the primary value displayed
 *   tone     default | info | success | warning | destructive | accent | muted
 *   active   boolean — highlighted state
 *
 * Slots:
 *   leading  optional icon / avatar
 *   default  primary content
 *   trailing optional right-aligned actions
 *
 * Events:
 *   ship-select  CustomEvent<{ value: string }> — user activated the element
 */

import { LitElement, css, html } from 'lit'

export class ShipMyThing extends LitElement {
  static properties = {
    value:  { type: String, reflect: true },
    tone:   { type: String, reflect: true },
    active: { type: Boolean, reflect: true },
  }

  value = ''
  tone = 'default'
  active = false

  static styles = css`
    :host {
      display: flex;
      align-items: center;
      gap: var(--space-2);
      padding: var(--density-row-py) var(--density-row-px);
      background: var(--surface-1);
      color: var(--foreground);
      border-radius: var(--radius-md);
      transition: background var(--duration-fast) var(--ease-out);
    }
    :host(:hover) { background: var(--hover-bg); }
    :host([active]) { background: var(--selected-bg); }
  `

  render() {
    return html`
      <slot name="leading"></slot>
      <slot></slot>
      <slot name="trailing"></slot>
    `
  }
}

customElements.define('ship-my-thing', ShipMyThing)
```

Then re-export from the pack's `index.ts`:

```ts
export { ShipMyThing } from './ship-my-thing'
import './ship-my-thing'   // side-effect: registers the element
```

## Token consumption

Components read tokens with bare `var(--foo)`. No fallbacks, no
hardcoded colors, no `oklch(...)` literals, no TS token constants.

The four-layer token taxonomy (semantic surfaces, tone ramps,
role-based typography + density, primitives) lives in
[ship-themes](/reference/themes/). Reach for the **highest layer that
fits** — `var(--surface-1)` before `var(--gray-100)`, `var(--tone-success-fg)`
before reassembling a `color-mix(...)` by hand.

If a pack component accepts a `tone` attribute, import `toneVars` from
`@ship/set`'s `web-components/util` and read `var(--tone-fg)` /
`var(--tone-bg)` / `var(--tone-border)` / `var(--tone-ring)` in your
CSS. The helper routes the host's `[tone="…"]` attribute to the right
ramp automatically.

See the full charter for exhaustive token tables:
`.ship/skills/ship-components/SKILL.md`.

## Shadow DOM, slots, parts

- Always `{ mode: 'open' }` (Lit's default).
- Always declare `:host { display: ... }`. Never leave it undefined.
- Content goes through **slots**, not attributes. `title` / `description`
  / `body` attributes for arbitrary text are a smell — use named slots
  (`leading`, `title`, `meta`, `trailing`, `actions`).
- Expose wrapped native elements via `part="button"` / `part="input"`
  so consumers can style them: `ship-my-thing::part(button) { … }`.
- No inline `<style>` via `innerHTML`. Use Lit's `css` template.

## Events

- All events are `CustomEvent` with `{ detail: {...} }`.
- `bubbles: true, composed: true` (cross shadow boundaries) unless you
  have a documented reason not to.
- Named `ship-<verb>` for user-initiated actions (`ship-select`,
  `ship-dismiss`, `ship-toggle`) or `ship-<noun>-<verb>` for state
  transitions on a sub-entity (`ship-tab-change`).
- Document every event in the component's header comment with its
  `detail` shape.
