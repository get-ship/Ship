Ship is an operating environment,
not a dashboard.

Three modes, three chromes. Desktop is the launcher for the user's apps — dock, widgets, a status strip. User apps run full-bleed; Ship's chrome disappears so the app owns the screen. Studio is Ship's own configuration surface — a separate world with its own rail, entered from the desktop or ⌘,. No mixing.

Decisions What this frame commits.

  1. D1 Three modes, three chromes. Desktop (dock + widgets), User app (none), Studio (rail). No surface borrows another's chrome.
  2. D2 Dock = user apps. Canvas, Sessions, Artifacts, Git, Events, Mesh, Prompt — and whatever the user builds. Studio + Settings sit on the dock as escapes (after a divider), not as "apps".
  3. D3 User apps run full-bleed. Zero Ship chrome. One persistent 24px home dot top-left (⌘. returns to Desktop; ⌘, opens Studio). No menubar, no breadcrumb, no rail.
  4. D4 Studio is pure config. Three rail groups: Configure (project scope, .ship/: agents · skills · components · themes · pipelines · project), Defaults (user scope, ~/.ship/: permissions · MCP · harnesses), Explore (remote: library · publishing). No work surfaces. Library lives here, not on the desktop.
  5. D5 Scope = rail group, not switcher. Per audits/scope-model.html: Defaults is a top-level rail group; project is inside Configure; agent overrides are inline in agent detail. No flat /permissions, /mcp.
  6. D6 Distribution is metadata, not navigation. bundled project user library — a card pill, same vocabulary everywhere a thing appears.
  7. D7 Library deep-links into editors. Opening a Library item lands on the same Configure › <domain> surface project-authored items use. One editor, two entry points. The "from library" pill is the only visible difference.

Open Q Still to resolve.

  1. Q1 How does Studio enter / exit? Lean: ⌘, opens (modal-style, slides over desktop), ⌘. closes. Dock item too (after divider). Confirm whether Studio replaces the desktop or layers over it.
  2. Q2 First-party views (Canvas, Sessions, Artifacts) — apps or chrome? This mock puts them on the dock as apps — i.e. they run full-bleed just like a user-authored view. Confirms Ship's own views eat its own dog food.
  3. Q3 Home dot — required, or pure keystroke? Some users hate persistent chrome in their app viewport. Alternative: no dot, just ⌘. + a momentary toast on launch reminding the user. Test before committing.
  4. Q4 Pipeline runs — Sessions or Pipelines? Definition is in Studio › Pipelines. Live runs need a home — a "Pipelines" user app on the dock that mirrors Sessions for pipeline-shaped work, or fold into Sessions with a kind filter?
  5. Q5 Status strip stays in Studio? The top strip in Mode 01 carries project/branch/run-count. Studio has its own top (with Studio badge + Close). Open: do we duplicate the strip into Studio, or trust the badge as enough orientation?
  6. Q6 Customizable dock? Users probably want to pin their own apps + reorder. Where does that affordance live — Studio › Project (per-project dock) or Defaults (across all projects)? Lean: both, with project override of user defaults.
