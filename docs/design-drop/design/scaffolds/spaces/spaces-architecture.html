Domain design brief — scaffold & component surface
00  The premise

A space is an app, not a tab. Ship gives it a window and a place to live.

Every space runs as its own OS window, its own process, its own launcher on the host — 100% user-owned pixels. This brief draws the one line that organizes the whole domain: what Ship ships as scaffold versus what the user builds as components — and designs both against the real ship.css token system and the SpaceService contract.

01  Topology

One hub. Many spaces. One daemon underneath.

The shape that everything else follows. The hub is a single privileged app — registry, studio, authority, account. Spaces are N independent windows. They never talk to each other directly; the daemon is the spine, and each space's connection carries its own implicit space context.

// the central app — ships with the binary

Ship Hub · one window

Spaces registry · Studio (the editor) · Authority queue · Marketplace · Activity · Account. The only surface that enumerates spaces, holds Activate, and grants capabilities. Privileged on purpose.

// user-owned — N windows, each its own process

Spaces · many windows

Each is a real OS app: own icon, own launcher (dock / Spotlight / Start menu / CLI), own theme & chrome. A space's connection is space-scoped, which is why Info / SetSetting / Watch(space) take no space argument.

02  The boundary — keystone decision

Where each piece lives: shipped scaffold, or user component.

You said the call is ours. Here's the proposed split. The rule: Ship owns the window contract and the chrome shell; the user owns identity, theme, content, and — eventually — the chrome's body. Anything a space can't be trusted to get right (OS registration, the title bar, the authority surface) stays scaffold.

08  Where I need you

Decisions that change the build.

Settled · settings

Settings are file-source + schema-backed, rendered as a rich UI — typed controls from the schema, not raw JSON. The settings page lives in the space (space-scoped, matching SetSetting / Watch(space)), not in a hub Studio.

Settled · views

There are no first-party spaces. A space is a user surface; Ship ships default views a user can adopt — dashboard, docs, canvas, inbox — as starting points on the same scaffold.

Next · the surface

Designed next, see space-settings.html: the per-space settings page with the chrome customizer (rail vs dock vs none) driving a live preview, the schema-backed rich settings, and the adoptable default views.

Then · to SUI

From there I author the load-bearing piece as real .sui + demo — ship-space-frame (the scaffold) or ship-setting-field (the rich schema control).
