`ship.*` ops are the read surface that view templates and the
`window.ship.*` JS SDK call. Every op is registered in
`apps/shipd/src/services/registry.rs` and described in
`apps/shipd/src/services/schema.rs::OPS`.

The canonical machine-readable catalog lives at
`packages/sdk/src/generated/sdk-ship-ops.json`, regenerated by `just
gen-sdk` and served live at `GET /api/ship/schema`. The lint rule
`ast-unknown-ship-op` (severity error) fails any template that calls
a name not in this catalog.

Calls accept keyword arguments (e.g. `ship.agents.detail(id="...")`)
and return JSON-shaped values. The dotted form `ship.try.<domain>.<op>`
runs the same dispatch but swallows errors — useful for tolerant
prefetches.

## Drift detection

The catalog is the single source of truth for three consumers:

- **Lint** — `crates/core/lint/src/rules/ast.rs` reads
  `sdk-ship-ops.json` at compile time. Calls to unknown ops fail
  `ast-unknown-ship-op` (severity error). Suggestions use Levenshtein
  ≤ 2 against the registered op set.
- **TS SDK codegen** — `window.ship.*` typed methods derive from the
  same JSON.
- **MCP auto-registration** — every op surfaces as an MCP tool when
  the project enables `ship.<domain>` capabilities.

Adding a new op is a three-step sync:

1. Add the dispatch arm in `apps/shipd/src/services/registry.rs`.
2. Add the matching `OpDescriptor` entry in
   `apps/shipd/src/services/schema.rs::OPS` (same name, same arg list).
3. Run `just gen-sdk` to regenerate `sdk-ship-ops.json`.

The match-arms-to-OPS pairing is intentional: `services::registry::names()`
derives the registered set from `OPS`, so a missing descriptor surfaces
as a runtime gap, and a missing dispatch arm surfaces as a 500 with
`unknown service` from the registry.
