# Agent access model

This is the end-to-end path by which a dispatched agent acts on Ship: from the
**skill** it reads, through the **capability** it holds, to the **transport** that
authenticates it. Three documents meet here — [the op surface](/reference/architecture/op-surface/)
(what ops exist and why), [the auth model](/reference/architecture/auth-model/)
(token paths + the gate), and this one (the agent's whole journey + the host
socket). Read this for "how does an agent call an op, and how do we know it's
that agent?"

The whole chain in one breath:

```
compiler emits capability-skills ─▶ agent reads SKILL.md ─▶ `ship ops call <op>`
        │                                                          │
        │ (proto descriptor = SSOT)                                ▼
        ▼                                              ship ops dials ship.sock
   gen-skills                                                      │ (no token)
                                                                   ▼
   supervisor spawns agent ──containerize──▶ ship-agent-<id> cgroup
                                                                   │
                              daemon reads SO_PEERCRED ◀───────────┘
                                     │
              resolve(pid) → process_container → Agent(<id>) → AuthContext → gate
```

## 1. The agent interface: capability-skills

An agent never sees a token, a URL, a port, or a socket path. Its entire
contract with the daemon is one CLI verb:

```bash
ship ops call <op-name> --json '<args>'
```

A **capability-skill** is a generated skill that teaches exactly this. One skill
per domain (`ship-git`, `ship-pipelines`, `ship-rules`, …). The agent loads the
domain's `SKILL.md` — a cheap table of contents — and opens a per-op reference
page only when it's about to call that op. This is OpenAPI-level progressive
disclosure, three tiers:

1. **`SKILL.md`** — frontmatter (`name: ship-<domain>`, one-line description, op
   count) + a list of every op with a one-line summary, each linking to its page.
2. **`references/docs/<op>.mdoc`** — per op: the description, the policy line
   (read `C0` / command `[blast]` + the required capability), an **Arguments**
   table (field · type), a **Returns** type with a field table, and a real
   **Example response** inlined from the op's fixture.
3. **The op itself** — invoked transport-agnostically via `ship ops call`.

Because the teaching is just `ship ops call`, the transport underneath can change
(TCP→socket, host→sidecar) without touching a single skill. `ship ops` is the
indirection that absorbs it.

## 2. How skills are generated

The **proto descriptor is the single source of truth** (decision #67a). Each op
is a method on a per-domain Connect service under `proto/ship/ops/v1/*.proto`,
carrying its policy as method options: `capability`, `blast_radius`,
`op_sensitive`, and `description`.

`cargo xtask gen-skills` reads the compiled `FileDescriptorSet` (via
`ship_ops_rpc::policy::read_policies()` — the same descriptor the gate reads) and
renders the skill tree. Input/output message types and their fields come from the
descriptor too, so the Arguments and Returns tables are never hand-maintained.
The **Example response** is pulled from `proto/fixtures/`, generated by
`cargo xtask gen-fixtures` against the same descriptor. One generator, one source,
zero drift — a completeness gate test fails if any documented op lacks a fixture.

<ship-alert tone="info">
Skills are <strong>generated artifacts</strong>: every <code>.mdoc</code> carries an
<code>AUTO-GENERATED … Do not edit</code> banner. Change the proto, regenerate —
never hand-edit a capability-skill.
</ship-alert>

Only **agent-facing** ops are rendered. The audience axis (#95) keeps operational
writes (`actor.*`, `mesh.*`) out of agent skills — agents get reads + the domain
commands they can actually be granted.

## 3. Capabilities: declared, granted, tracked

Identity answers *who*; the **gate** answers *may they*. The model is
**caller × blast-tier × per-service ceiling** — the two axes that already exist
(the proto **service** and the op's risk **tier**), **no separate capability
taxonomy**. Enforced once at the dispatch chokepoint (`services::gate::decide`,
invoked by `services::command::call`) — identical over every transport. Full table:
[the auth model](/reference/architecture/auth-model/).

- **`requires:`** is what a workflow/app *declares* it needs (public, authored).
  **Skills don't `grant:`** — that field is retired; the user grants, the runtime
  manages. An unmet requirement surfaces at compile/install.
- **`blast_radius`** is the op's risk tier (`C0 < C1 < C2 < C3`): **C0** read ·
  **C1** workspace-write · **C2** elevated (dispatch/stop/steer, authoring) ·
  **C3** critical (account/billing/permissions/`agent.grant`). Unrecognized →
  fails closed to C3.
- **Authority** = a default **C1 ceiling** (every agent reads + workspace-writes
  anywhere — the operational baseline) plus the **services it's elevated in** (the
  C2 set). The gate allows a C2 op only when its service is in that set; **C3 is
  operator-only, never an agent**. The service is the op's domain (`domain_of`).

### The grant source: provisioned baseline (#85)

An agent's **elevated services** are operator-approved server-side state, not a
claim the agent makes. `resolve_grants(agent_id, role)` is **provisioned-wins**: it
reads the per-agent baseline from the `provisioned_grants` projection; if a baseline
exists it fully replaces the role default; otherwise it falls back to the role's
elevated set (`grants_for_role`); unknown → empty (fail-closed, C1-baseline only).
The baseline is changed only via `provision_grants` (operator/daemon authority —
the agent can edit its skill files but not its elevated services).

### Tracking

Grant provisioning is **event-sourced**: `provision_grants` appends an
`agent.grants.provisioned` event (`AgentGrantsProvisioned { grants, source,
approved_by }`), and the `provisioned_grants` projection is rebuilt from the log.
The append is transactional-with-projection, so the next `resolve_grants` sees the
change immediately. Every grant an agent has is therefore attributable to an event
with a source (`install` | `operator`) and an approver — auditable, tamper-evident
by the log.

## 4. The host transport: unspoofable per-agent identity

On the token path (TCP/REST, browser + operator CLI) the caller proves identity
with a bearer token. **Agents get no token.** Instead the daemon binds a unix
socket and reads each caller's identity from the kernel.

**`<daemon_dir>/ship.sock`** — bound `0600`, best-effort, alongside TCP (TCP stays
the primary surface; a socket failure never takes the daemon down). It serves the
*same* app and the *same* gate. The difference is only where `AuthContext` comes
from.

The identity chain, link by link:

| Step | Where | What happens |
|------|-------|--------------|
| spawn | `spawn_actor` → `ship_host::containerize` | the agent process is placed in a `ship-agent-<id>` process container |
| dial | `ship ops` (`apps/ship-cli/src/ops_cmd.rs`) | when `ship.sock` exists, dial it — **no token** — else TCP+token |
| accept | `PeerCredInfo` (`apps/shipd/src/auth/peer_socket.rs`) | read `SO_PEERCRED` off the connection → kernel-verified peer **PID** |
| resolve | `peer_identity::resolve(pid)` (ship-platform) | `process_container(pid)` → `ship-agent-<id>` → `PeerIdentity::Agent(id)` |
| bridge | `auth_context_from_peer` (shipd) | `Agent(id)` → `AuthContext { Mcp, agent_id, grants: resolve_grants(id) }` |
| gate | `services::gate` | unchanged — the socket-built `AuthContext` is just another caller |

`auth_middleware` short-circuits when an `AuthContext` is already present, so the
peer-cred middleware (socket) and the token middleware (TCP) are two sources
feeding one gate — no parallel auth model.

Why it's unspoofable: a process **cannot forge its PID to the kernel**, and it
cannot join another agent's process container without privilege. The agent sends
no identity claim at all — the kernel reports who is calling and the daemon owns
the PID→agent map. This is what the token path's "MCP session role claim"
limitation never had: a per-agent credential the agent cannot mint or lie about.

<ship-alert tone="warning">
This is identity + least-privilege, <strong>not</strong> a Tier-1 isolation
boundary. A host agent shares the user's uid and can act outside the daemon. The
container gives unspoofable <em>identity</em> (and the hook for Tier-1 resource
isolation later); the real trust boundary for untrusted work is Tier-2+ sandboxing.
</ship-alert>

## 5. Per-OS compatibility matrix

Everything OS-specific lives behind `ship_host::HostOs` — one adapter per
platform. Two primitives matter here: reading a connection's peer identity, and
placing a spawn in a per-agent container.

| Platform | Transport | Peer identity | Named container | Per-agent auth |
|----------|-----------|---------------|-----------------|----------------|
| **Linux + systemd** | `ship.sock` | `SO_PEERCRED` ✅ | systemd transient user scope (`ship-agent-<id>.scope`) ✅ | **working** |
| **WSL2 + systemd** | `ship.sock` | `SO_PEERCRED` ✅ | systemd transient scope ✅ | **working** (this dev host) |
| **WSL2 / Linux, no systemd** | `ship.sock` | `SO_PEERCRED` ✅ | none (no delegation; raw cgroupfs *not built*) ⚠️ | operator only |
| **macOS** | `ship.sock` | `LOCAL_PEERPID` + `getpeereid` ✅ *(written, unverified on hw)* | process-group (`setpgid`) — *pending* | operator only |
| **Windows** | **TCP + token** | n/a (AF_UNIX has no peer-cred) | job object — *pending* | token path |

How a platform without a **named** container resolves identity — `peer_identity::decide`:

- An **agent** is named by its container (`ship-agent-<id>`) → `Agent(id)`.
- A **container that isn't an agent's**, or **no container on a platform that has
  no backend** (macOS today): a peer running as **our own uid is the operator**.
  The `0600` socket already restricts callers to our uid; the uid check is
  defense in depth. A foreign uid never resolves.
- **No container where a backend *does* exist** (Linux): **fail closed**
  (`Unresolved` → 401). An unreadable cgroup could be a transient `/proc` race on
  a real agent — we never promote that to operator.

So "operator only" means: the socket authenticates and the **operator** works
fully, but agents resolve as the operator too (no per-agent differentiation)
until that platform's container backend lands. Safe by default — it never
mis-attributes one agent as another, and never silently grants C2.

**Windows** is wholesale on the token path today: `ship.sock` is `cfg(unix)`, so
the daemon never binds it and `ship ops` never finds it → TCP + operator token.
Per-agent identity there needs a **named pipe** (`GetNamedPipeClientProcessId`) +
job-object container — a separate transport, not `ship.sock`.

Detection is cheap and cached: the Linux backend uses systemd only when the user
manager is live (the `$XDG_RUNTIME_DIR/systemd/private` socket exists) and
`systemd-run` is on `PATH`. `SHIP_NO_CONTAINERIZE=1` forces the bare-spawn
fallback.

## 6. Known limitations

- **macOS container backend is pending; its peer-cred is written but unverified.**
  `peer_cred` has a macOS arm (`LOCAL_PEERPID` + `getpeereid`) authored against
  the documented libc API but **not compile-verified on macOS hardware** (this
  dev host is Linux) — validate on a Mac. With it, the operator works over the
  socket; agents resolve as operator until the process-group container backend
  (`setpgid`) lands. **Windows** has no AF_UNIX peer-cred, so it stays on the
  TCP+token path until a named-pipe transport exists.
- **`systemd-run` is not portable and is not bundled.** It's a thin D-Bus client
  to PID 1 — useless without a running systemd, and Linux-only. It is *one Linux
  backend strategy*, detected at runtime, never the universal mechanism. The
  portable contract is the `HostOs` trait, not the tool.
- **WSL without systemd** has no container backend (root-owned `/init.scope`, no
  cgroup delegation) → operator fallback.
- **Raw cgroupfs backend is unimplemented.** Only the systemd transient scope
  exists today; a delegated-cgroupfs path for non-systemd Linux is future work.
- **Role refinement on the socket path.** `resolve` resolves grants via
  `resolve_grants(id, None)` — correct (provisioned-wins) for any provisioned
  agent, but the role fallback for *un-provisioned* agents isn't yet threaded from
  the agent record into the socket middleware.
- **Tier-1 caveat** (above): identity ≠ isolation for host agents.
